H

HarnessGrad

一个用来运行和比较 harness 自进化方法的平台。 我们不提出又一个方法 —— 我们造那台让不同方法第一次可以被放在一起比较的仪器。

1问题：每个方法都报一个分数，但没有一个能比

harness 自进化（RSI）这个方向出了一批方法，每个都报告自己的分数涨了多少。 但没有一种能说清那个涨幅是由什么构成的，也没有一种把它报在一条能和别的方法对比的曲线上。

把两个方法并排放在一起时，你几乎立刻会遇到这些问题：

你想要的比较现实
同一个起点每个方法自带自己的 harness，起点不同
同一批题各自在自己的 benchmark 上跑，任务集不同
可信的分数分数常常由方法自己报，或者由它自己的 runner 记
知道涨得是否显著通常只有一个点估计，没有区间
知道涨在哪「方法改了 harness 的哪些文件」很少有记录

结论是：这个领域缺一个共同的训练信号。缺的不是方法，是仪器。

2我们的选择：把仪器和方法分开

HarnessGrad 是一个平台。它定义并拥有「测量」这件事，然后把「怎么改进 harness」完整地留给外部。

平台拥有方法与 harness 拥有
跑哪些题、跑几轮从轨迹里读任何它想读的东西
执行 harness、收集轨迹决定怎么修改 harness
全部评分—
每一个曲线点、状态快照与 token 计数—

评分不可委托。一个给自己打分的主体，会让所有跨方法比较同时失效 —— 它不是在被测量，它是在给自己批卷子。这一条是整个设计里唯一不能让的东西。

为什么方法必须在 harness 之外

最早的设计把方法放在 harness 内部。那让它和一件产物绑死：它只能改进它自带的那只 harness， 而两个方法无法比较，因为它们面对的是不同的起点。把方法放到外面，才让 「同一个方法用在任意起点上」成为可能。

方法通过子进程调用，永远不 import。这不是风格选择：一个被 import 的模块在加载时 就被冻结了，而这个平台存在的意义正是测量一只会重写自己改进机制的 harness —— import 会让那种情况无法被表达。

3三个词，然后就能看懂全部

harness

一个能独立解一道题的目录：一个入口、一份清单、它需要的代码。 它是被进化的东西。用 git 做版本：commit 是检查点，prefix 是回滚。

method

一个外部进程。它拿到一份干净的起点副本，读轨迹，产出候选 harness； 平台再去测那些候选。它可以是任何语言写的。

agent = harness + model

被测量的对象是两个东西的组合。所以一个分数必须同时说清是哪只 harness、 哪个模型测出来的 —— 换模型就是换仪器，两条曲线不能画在一起。

一次运行只关于一侧 这是最关键的一条

训练运行 train

方法看得到这些题的轨迹，用来自我诊断。分数会被拟合抬高 —— 它是进度，不是成绩。

考试运行 eval

测某个训练状态一次，方法完全不参与。考试题的轨迹结构上不在训练运行里。

这里的「不在」是字面意思，不是靠隐藏字段做到的：跑训练时，考试那一侧从不被加载， 它的题不评测、它的轨迹不写出。于是「方法看不到考试」不再是一条需要被信任的规则， 而是一个不存在的东西。考试运行则指回它测的那个训练轮次，两者在图上连成一对。

4一次运行长什么样

  ① 门口 —— 在花掉任何算力之前
    检查模型可用      声称是真实模型却连不上 → 每个分数都不可信,提前停
    按侧别收窄        另一侧从此不在这次运行里
    检查能力匹配      harness 声明不了这类环境 → 提前拒绝
    固定镜像摘要      解析不出就拒绝启动
    建好隔离边界      建不起来就停,绝不降级成「没有沙箱」

  ② 第 0 轮：基线
    把起点提交为 H0 → 测量 → 写下第一个曲线点

  ③ 每一轮
    调用方法 → 得到候选 harness → 平台自己测量它
    → 保存这一轮的状态 → 曲线追加一行(立即落盘)

  ④ 产物
    一条曲线 · 每一轮的 harness 状态 · 轨迹 · 每一次拒绝的理由

曲线点里有什么

这是上面那条命令真实产出的一个点（删掉了重复的细节）：

{
  "run_id": "quickstart", "round": 1,
  "side": "train", "score_kind": "training",
  "score": 0.0, "score_ci95": [0.0, 0.0], "n_scored": 4,
  "measured_by_platform": true,

  "identity": {
    "harness_sha": "fc2b63b323f2…",        // 状态:这一次测的到底是哪只 harness
    "agent_model": "qwen3.5-9b-local",   // 决定分数的模型
    "method_model": "qwen3.5-9b-local"   // 决定改什么的模型(分开记账)
  },

  "editable_surface_touched": [],           // 从 git diff 读出来的,不是方法自报
  "verifier_kinds": ["answer"],              // 只记种类,绝不记它的参数
  "env": { "kind": "files", "image_digest": null },
  "cost": { "evaluation_trials": 4, "harness_model_calls": 32,
             "wall_clock_s": 0.6 }
}

为什么这些字段，为什么只有这些。曲线点会被写进方法能读到的通道， 所以每多一个字段都是一次泄漏面的扩大。verifier_kinds 只写验证器的种类， 绝不写它的 argv 或标准答案 —— 那等于把方法正在被怎么评分告诉它。

editable_surface_touched 是读出来的：[] 表示方法只返回了原样， ["agent.py"] 表示它真的改了 harness。平台没有「真 RSI 模式」这个开关 —— 一个声明的模式只是自述，而「真/伪」是一个读数。

5为什么这些数字可以被相信

四条，每条都尽量做成结构性的，而不是「我们保证会检查」。

① 平台靠「不被挂载」而看不见

harness 跑在自己的挂载命名空间里，平台的目录根本不在它的磁盘上。 不是靠检查它读了什么 —— 是它够不到。

② 环境被固定到镜像摘要

一个 tag 会移动，一个 digest 不会。解析不出摘要，运行就拒绝启动 —— 而不是记下一个会漂移的 tag 然后称之为可复现。

③ 评分器是平台的，方法看不到

任务、初始状态、评分逻辑都在平台侧。方法拿到的是任务描述，不是答案。

④ 平台给自己做哈希

每次方法调用、每次评测前后，平台对自己的文件取哈希。任何东西动了， 这次运行就失败，并指名被改的路径。

我们刻意把三种主张写成三种状态。「harness 不能靠 .. 走到平台」是强制执行的； 「harness 完全够不到平台」只是被检测的 —— 因为主体以同一个用户运行时，绝对路径仍然够得到一切。 把这些都写成「已保证」，会让这个平台最容易被误引用的那句话变成假话。

失败是被说出来的，不是被降级掉的

一次静默降级产生的数字，含义和它自己声称的不是一回事。所以平台有大量「拒绝启动」的分支， 而且每一条都会把理由写进运行的记录里。几个例子：镜像不在本地就拒绝（平台绝不在运行中途拉取任何东西）； 隔离边界建不起来就拒绝，绝不改用「没有沙箱」跑一遍；一道题都没能测出结果时拒绝， 而不是记一个 0.0 —— 那会在一只 harness 根本没跑过的运行上写「它得了零分」。

6现在能跑什么

已有的
数据集 若干自带的验证集（文件类、容器类、服务类）与 Terminal-Bench 2（89 道真实任务， 按哈希划分为 52 训练 / 37 考试）
起点 harness 5 只，包括一只 oracle 对照 —— 它跑数据集自带的参考解， 用来回答「这道题在这里到底够不够得着」。够不着的话，任何关于 harness 的结论都建在一个空检查上。
方法 两种执行模式：Mode A 平台拥有循环、每轮要一步；Mode B 方法跑自己的搜索、 返回整条轨迹（为那些已经存在、不该为了被测而改接线的方法准备）。另有若干已发表方法的移植。
界面 一个本地控制台：选配置跑一次实验、看历史结果、以及一张按 (harness · base model) 分泳道的版本图，每个圆是一轮，虚线连出 「考试测的是哪个训练轮次」。

7五分钟跑起来

依赖只有三样：bubblewrap、git、python3 ≥ 3.10。 平台本身零第三方 Python 包。安装脚本不会停在「bwrap 装上了」—— 它会真的建一个命名空间并在里面找自己，失败就说清原因。

# 1. 装依赖并验证隔离真的能工作
./install.sh

# 2. 跑一次最朴素的控制组:起点不变,只测它自己
#    (先不接真模型,用 mock 后端确认整条链路是通的)
HG_AGENT_BACKEND=mock python3 driver.py \
    --harness loop_plain --mode A --rounds 1 --run-id quickstart \
    --method-entrypoint "python $PWD/methods/noop/run.py"

# 3. 看结果
python3 tools/plot_curve.py runs/quickstart

你会看到这样一份读数：

  harness   loop_plain 0.1.0-control
  data      demo · 4 tasks on the train side · train 4 / eval 4
  model     qwen3.5-9b-local · mock   ← not a live model
  sandbox   bwrap active — the harness cannot see this directory

  ! this run scores 4 tasks — the score moves in steps of 0.250
  round 0  H0 (base harness)           train 0.000
  round 1  base harness (control)      train 0.000   · no change reported

那次 mock 标记和那句步长提示都是设计的一部分：一个分数旁边必须写着它是谁测的、 在几道题上测的，否则读的人会以为 0.000 是一件关于 harness 的事实。

8我们刻意没做的事

  • 不提出方法。我们造仪器，所以不和我们要测量的方法竞争。
  • 不做自评。分数永远出自平台，永远带区间和任务数。
  • 不为了「能跑」而放宽契约。九种已发表方法我们适配过，没有一种的原生形态是 「一个能独立解一道题的目录」。契约本可以放宽 —— 接受一个引擎、一份凭证、一个沙箱 —— 但它没有：什么都能跑的平台，什么都测不出来。 适配器只有两件事可做：把产物变成自足的，或者诚实地报告它不是。
