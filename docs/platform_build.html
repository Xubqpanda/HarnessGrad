HarnessGrad：这个平台是怎么搭的

这份是技术细节版，写给已经知道这个项目、要看实现理由的人。 第一次接触的话，先看 docs/intro.html —— 一页纸的定位与核心概念。

一句话：我们不提出一个 RSI 方法，我们造那台让 RSI 方法可以互相比较的仪器。 所以平台拥有「测量」，而把「怎么改进 harness」完整地留给外部。下面记录的是这台仪器的 构造方式、每条规则背后的理由，以及哪些结论是实测出来的而不是推定的 —— 这个区分在这个项目里是硬要求，因为它决定了哪句话可以被引用。

9个平台自有模块（eval/）
316例质量测试（314 通过 / 2 跳过）
1695行冻结的接口契约 INTERFACE.md

这是什么

每一个 harness 自进化方法都报告一个最终分数增量。没有一种能说清那个增量是由什么构成的， 也没有一种把它报在一条能和别的方法对比的曲线上。这个领域缺一个共同的训练信号。

HarnessGrad 定义的那个信号

一个 base harness · 一个固定的任务集 · 一个采样循环，以及一个曲线点，记录：

  • harness 状态（harness.json 的 sha，以及它在 git 里的提交）
  • 涉及的两个模型 —— agent 模型（决定分数）与 方法模型（决定改什么）
  • 分数与 95% 置信区间，以及是在几道题上测的
  • 拿到这个分数花掉的算力（token、wall clock、评测次数）

分工边界

整个设计只有一条不能让步的线：评分不可委托。一个自己给自己打分的主体， 会让所有跨方法比较同时失效 —— 它不是在被测量，它是在给自己批卷子。

平台拥有Harness（及其方法）拥有
跑哪些题、跑几轮从轨迹里读任何它想读的东西
执行 harness、收集轨迹决定怎么修改 harness
全部评分—
每一个曲线点、ckpt 与 token 计数—

这条线在代码里的体现是 PLATFORM 这个元组 —— 它同时也是完整性校验的名单： 

# eval/integrity.py
PLATFORM = ("driver.py", "eval", "ckpt", "data", "tools", "methods",
            "tests", "docs", "INTERFACE.md", ".env")

base_harness/ 故意不在这份名单里。它是候选者，不是裁判：每次运行都先把它复制进工作区， 被编辑的是那份副本。把它列进来会让「平台唯一要做的那次写入」被标成篡改。

一次运行的流程

  ① 门口（任何东西被支付之前）
    模型可用性检查          backend 是 live 但 key 没配 → 每个分数都会来自一个够不到模型的 harness
    加载数据集 + split      按侧别收窄 —— 另一侧从此不在这次运行里
    能力门禁 env_kinds      harness 声明不了的任务,提前拒绝(见 §拒绝路径)
    镜像摘要解析            §2.5.4:解析不出 digest 就拒绝启动
    容器/沙箱边界构建        边界建不起来就停,绝不静默降级成主机上跑
    工作区在平台之外         拒绝任何让 harness 能用 .. 走到平台的路径

  ② round 0：基线
    commit H0 → 在工作区里评测 → 写曲线点 → 保存 state_after_round0/

  ③ 每一轮
    调用方法(子进程) → 拿到候选 harness → 平台自己测量
    → 写 state_after_roundN/ → 曲线点追加一行(立即落盘)

  ④ 出口
    curve.jsonl / events.jsonl / traces / launch.json / console.log

曲线点是逐条追加并立即落盘的，不是最后一次性写出。一次被中断的运行曾经会在磁盘上 留下上一次运行的 curve.jsonl，于是控制台画出一条属于另一次运行的曲线。

三个对象

harness

一个能独立解一道题的目录。它是被进化的东西。 用 git 做状态：commit 是检查点，prefix 是回滚，相同 prefix 天然去重。

method

一个外部进程。它拿到一份干净的 base harness 副本， 产出候选 harness；平台再自己去测那些候选。

agent = harness + model

被测量的对象是两个东西的组合。所以曲线点必须同时记录 harness 的 sha 与 agent 模型的标识。

为什么方法必须在 harness 之外

最早的设计把方法放在 harness 内部。那让它和一件产物绑死：它只能改进它自带的那只 harness， 而两个方法无法比较，因为它们面对的是不同的起点。

把方法放到外面，才让「同一个方法用在任意 base harness 上」成为可能 —— 也正因如此，方法不再能是被测量对象的一部分。

方法通过子进程调用，永远不 import。这不是风格选择：一个被 import 的模块在加载时 就被冻结了，而这个平台存在的意义正是测量一只会重写自己改进机制的 harness。 import 不会让那种情况变复杂，它会让那种情况无法被表达。

交换单位与清单

交换单位是整个 harness 仓库，不是一段代码。它必须自己声明自己：

// harness.json —— 清单（必需）
{
  "name": "loop",
  "version": "0.2.0",
  "entrypoint": ["python3", "agent.py"],
  "env_kinds": ["files", "exec"],   // 它能在什么环境里工作
  "role": "harness"            // 或者 "control"
}

harness 是一条命令，不是一种语言

入口是 argv 数组，不是「一个 Python 函数」。所以一只用 shell、Go 或 Rust 写的 harness 和一只 Python harness 在这个平台上是同一等公民 —— 平台只负责在正确的环境里执行那条命令。

一次运行只关于一侧 §2.6

这是最近一次重要的契约修订，也是整个评测可信度的承重墙。

train 训练运行

方法看得到轨迹，用来自我诊断。分数会被拟合抬高 —— 它是进度，不是成绩。

eval 考试运行

测某个训练状态一次，方法完全不参与。考试题的轨迹结构上不在训练运行里。

收窄是结构性的，不是靠一层字段遮蔽：

# driver.py
# 另一侧从不被加载、从不被评测、它的轨迹从不被写出。于是
# 「方法看不到考试」不再是一个平台扣住的字段,而是根本不在这
# 次运行里的一侧。
side_ids = list(split[args.side])
tasks_all = [t for t in tasks_all if t["task_id"] in set(side_ids)]
setups, verifiers, envs = _narrow_to_run(setups, verifiers, envs, side_ids)

这一行曾经是漏的。收窄只作用在任务清单上，而 load_envs / load_tasks 读的是整个数据集，于是三个表里都留着另一侧的条目。后果是实测到的： --side train --tasks break-filter-js-from-html 被一道 eval 侧题目的缺失镜像 alexgshaw/mteb-leaderboard:20251031 拒掉了 —— 一次根本不会碰它的运行。

被拒绝的读法不是「少了一个镜像」，而是「它无视了我选的题」，这比拒绝本身更糟。

eval 运行指向它测的那个状态

{
  "side": "eval",
  "score_kind": "exam",
  "evaluated_from": {
    "run_id": "ui-train",
    "round": 1,
    "harness_sha": "87f9412d234876edca9002008183a769b3d1383c"
  }
}

连接键是 evaluated_from.harness_sha，不是这个 eval 点自己的 identity.harness_sha。原因是实测的：eval 会重新提交它暂存的状态，于是拿到一个不同的 sha （量到 87f9412d… 对 8748bb05…）。用后者去连线会连不上任何东西。

为了让 eval 有东西可指，每一轮的状态都以 runs/<id>/state_after_round<N>/ 落盘， round 0 也包括 —— 「在考试上测 H0」是后面每一次 eval 的读数基准。

曲线点记录什么

曲线点会被写进方法能读的通道，所以这里每多一个字段都是一次泄漏面的扩大。

字段为什么它在为什么别的字段不在
identity.harness_sha 状态是测量对象的身份 —
agent_model / method_model 两个模型，分开记账；换模型就是换仪器 曾经只记一个 mock，而真实模型在回答每一道题
score + 95% CI + n_tasks 没有区间的分数不可比较 —
env.image_digest §2.5.4：tag 会移动，digest 不会 只写 tag 等于把「不可复现」写成了「可复现」
verifier_kinds 只记验证器的种类（answer / command） 绝不记它的 argv 或 expected —— 那等于把方法正在被怎么评分告诉它
measured_by_platform 区分「平台测的」与「方法自己报的」 缺这个字段会让记录声称分数是方法自己给的 —— 与事实相反
editable_surface_touched 从 git diff 读出，不是方法自报 method/accept.py 出现在这里意味着方法改写了自己的接受规则

平台没有「真 RSI」模式。一个声明的模式只是自述；「真/伪」的区别是一次读数， 不是一个设置项。所以 editable_surface_touched 是读出来的： [] 是只返回原样的对照，['agent.py'] 是真的改了 harness。

两种环境：files 与 exec

files

任务的文件是一个宿主目录，绑定挂载进容器。

  • 平台隐藏方式：不被挂载（bwrap 命名空间）
  • 运行时：宿主自己的解释器
  • 验证容易：平台能读、能冻结产物

exec

任务的状态在容器自己的文件系统里。

  • 平台隐藏方式：同样不被挂载 —— 这是第二道独立边界，不是替代品
  • 运行时、解释器、工具都是镜像的
  • network: none 才成为可能：容器有自己的网络命名空间

环境是声明出来的，连同资源与超时：

ENV = {"t01": {"kind": "exec", "image": "...", "workdir": "/app",
               "state": "container",        # 默认 "mount"
               "network": "bridge",
               "cpus": 1, "memory_mb": 2048,
               "agent_timeout_s": 900, "verify_timeout_s": 900,
               "services": []}}

容器状态：commit，然后在一个全新容器里验证 §2.5.9

Terminal-Bench 不是 mount 的形状：它的任务在自己的镜像里设 WORKDIR /app， harness 在容器的文件系统里工作。实测：镜像里 /app 是空的，指令说往 /app/ars.R 写，检查读 /app。用绑定挂载会把任务放到任务自己没放的地方。

十步

  1. 从已固定摘要的镜像启动任务容器；不做 workdir 绑定挂载
  2. 把 SETUP 拷进去（docker cp）—— 多数容器状态任务把环境装在镜像里，不需要这一步
  3. 运行 harness，--workdir 指向容器自己的工作目录
  4. harness 停止 → docker commit → 得到一个快照镜像
  5. 从快照启动一个全新容器
  6. 把 VERIFY 的输入拷到容器内的路径  ← harness 从没见过它们
  7. 创建存放 reward_file 的目录  ← 也没见过这个
  8. 运行检查
  9. 从 reward_file 读分数
  10. 删除快照镜像与任务容器

为什么这样能满足 §2.2 的三条不变量 —— 「提交整个文件系统」听起来像是「重新物化输入」的反面：

检查的输入

是 tests，在第 6 步、harness 停止之后才拷进来。 它们从不在镜像里，也从不在 harness 运行过的那个容器里。实测：真实的 Terminal-Bench 镜像里 完全没有 /tests，是平台在做这次拷贝。

任务状态

/app 以及 harness 碰过的任何东西，本来就该由 harness 控制 —— 那正是被评分的东西。快照是它被运送的方式。

快照是不可变的

它是一个镜像。检查跑在它的一个可写副本上， 检查写的任何东西随那个容器一起消失。检查无法改动它正在评分的东西。

比原版更严

全新容器比 Terminal-Bench 自己的 runner 更严格 —— 后者在 agent 待过的同一个容器里跑测试，于是 agent 放到后台的任何进程都被 reparent 到 PID 1，仍然在那里。 从快照起步让 §2.5.6 的保证在这里也成为结构性的，而不是尽力而为。

用 docker commit 而不是把 /app 拷出来， 因为检查可能读 /app 之外的地方 —— 实测：真实任务集在六处引用 /tmp/frame.bmp， 所以有一部分任务的产物放在只拷 /app 会丢掉的位置。

谁的解释器在跑 harness

镜像里有解释器就用镜像的，否则用平台的。两半都是必需的： §2.5.3 说在环境里跑 harness 的理由是「bash、文件编辑器和解释器都是镜像的」； 但任务镜像不保证有解释器 —— 真实的那个是 ubuntu:24.04 加一个 COPY， 没有 python3、没有 R、没有 gcc。

服务与模型网关

一个服务是模拟 API、数据库、浏览器或模拟用户 —— 必须在 harness 运行时同时活着， 且只能从任务环境内部到达。三条规则就是全部设计：

  • 每个任务一个 --internal 网络。不是每个运行一个 —— 任务 N 的服务 不能被任务 N+1 到达。共享网络会让每个任务都变成「有网络的任务」。
  • 生命周期跟随任务，不跟随运行。
  • 镜像同样固定摘要。一个被重新打过 tag 的 mock API 就是另一道题。

模型网关：容器里的 harness 怎么够到宿主上的模型

明显的那几条路全部失败，而且是量过的：

container → 127.0.0.1:8001           # 容器自己的 loopback
container → 172.17.0.1:8001          # 网桥网关;vLLM 只绑 loopback,那里没人监听
container → host.docker.internal     # Linux 上默认没定义
internal  → <它自己的网关>:8001      # 同上,没人监听

错误的答案是 --network bridge。那会让任务拿到互联网， 而「一个有网络的任务和一个没网络的任务不是同一个任务」（§2.5.4）—— 一道 exec 任务会因为平台投递模型的方式而悄悄变成一道联网任务。 正确的做法是在宿主侧起一个转发器，绑到那个内网自己的网关上。

完整性：能执行的就执行，剩下的靠检测

要让一次测量说明点什么，有两件事必须成立，而操作系统两件都不管。两条都是在这台平台上测出来的， 办法是跑一只入口会探测自己周围环境并汇报的 harness： 

up1/driver.py, up2/driver.py            absent      # `..` 上爬被关掉了
abs /…/HarnessGrad/.env                 READABLE
abs /…/HarnessGrad/driver.py            READABLE
abs /…/HarnessGrad/eval/metrics.py      READABLE
write /…/HarnessGrad/_probe             WROTE

只要主体以同一个用户运行，绝对路径仍然够得到一切。所以第二半是检测， 而保证实际上就住在这里 —— 平台在每一次方法调用和每一次评测前后对自己的文件做哈希， 任何东西动了就让这次运行失败，并指名路径。

主张状态
harness 不能靠 .. 够到平台强制执行 工作区被搬到平台之外
harness 完全够不到平台检测 每次运行哈希
方法完全够不到平台检测 每次调用哈希

三种主张、三种状态，是故意分开的。把它们都写成「已保证」会让这个平台最容易被误引用的那句 变成假话。

拒绝路径必须可见

这个平台有大量「拒绝启动」的分支 —— driver.py 里 18 处 return 2 加 23 条 error 级事件。设计约束是：拒绝永远不能是静默的。一次静默降级产生的数字， 含义和它自己声称的不是一回事，那是这个项目能犯的最贵的错。

情形平台的回答
镜像不在本地拒绝启动。平台不在运行中途拉取任何东西 —— 跑一半才发现要联网，会让「这次运行为什么停了」变成一个没法回答的问题
解析不出 digest拒绝启动（§2.5.4：没有摘要就没有运行）
harness 声明不了任务集需要的环境种类拒绝，并且排在最前 —— 这是「导入什么都没用」的那种失败，和「差一个镜像」不是一类
沙箱边界建不起来拒绝，绝不降级成 --no-sandbox
工作区落在平台树里拒绝 —— 那让 .. 又能上爬了
没有任何任务产出可评分结果拒绝，而不是记一个 0.0：mean([]) 是 0.0，那会在一只 harness 根本没跑过的运行上写「它得了零分」
跑了太少题照跑，但显式说出来：会打印这次运行的最小分差步长（例如 2 题 → 0.500）

那条关于题数的提示，文案本身就错过一次：它曾经写 eval side is N tasks， 而 N 是这次运行自己评分的题数。于是一次单题的 train 运行会宣布 「eval side is 1 tasks」—— 而考试侧有 37 题。一个关于错误对象的测量，读起来比没有提示更糟。

对照与可达性

base_harness/oracle 的 role 是 control。它不改进任何东西 —— 它运行数据集自带的参考解。

它回答的问题不是「harness 好不好」，而是「这道题在这里够不够得着」

如果 oracle 也拿不到分，那么这道题谁也拿不到， 而任何关于 harness 的结论都建立在一个够不着的检查上。它已经找出 3 个真实的平台缺陷。

在界面上它被单独分组，标注为「对照（不是 harness，不要引用它的曲线）」 —— 一个会被误当成方法结果的对照，比没有对照更糟。

方法的接口

两种执行模式，区别只在谁拥有调度：

Mode A · 平台驱动

平台拥有循环，每轮调用方法一次、要一步。 可比性最高。

Mode B · 方法驱动

方法在自己的进程里跑自己的搜索，写出整条轨迹； 平台解析并测量它指名的状态。为那些已经存在、不能为了被测而改接线的方法准备 —— RRSI 拥有一个退火的 20 轮预算，DGM 有一个 archive。

两种模式写同一种 curve.jsonl，所以来自任何一种的曲线都落在同一根轴上。

方法还可以拒绝一个候选（stop）—— 拒绝一个候选和「已经做完」不是同一件事。 以及 nominated：方法为哪一步背书。平台记录这些，但不解释它们。

九个适配器的发现

这一节记录的是一条历史结论，不是当前能力。它描述的 replay 路线已不再维护 （见 adapters/README.md）。活下来的是那个读数：下面这张边界表是平台记录 editable_surface_touched 而不接受一个声明模式的原因，也是为什么一次移植必须说明 「它的哪条规则是 Mode A 表达不了的」。

九个已发表方法被适配过。每一个都从不同方向撞上同一堵墙：

产物是什么方法平台为什么跑不了它
模块树 + 自己的 runnerRRSI没有入口；它由 harbor 驱动
archive 里的变体DGM由方法自己的容器脚手架调用
每轮复制自己的源码SICA在方法自己的 benchmark runner 下运行
gen_<id>/ + patchHyperAgents被拷进每运行一个的容器

一个 artifact 文件MAC需要 artifact 的 key 和 endpoint
一个 YAMLHarnessX需要 harnessx 包和模型配置
只有输出Meta-Harness它的接口里包含沙箱协议

这个平台的交换单位是一个能自己解一道题的目录，而没有任何已发表方法的 harness 是这个形状。 所以这份契约本可以放宽 —— 接受一个引擎、一份凭证、一个沙箱 —— 但它没有，理由只有一个： 一只 harness 能独立运行，是让两个方法可比的前提。什么都能跑的平台，什么都测不出来。

这给适配器只留了两件事，没有第三件：把产物变成自足的，或者诚实地报告它不是。 两种结果都记在曲线点上（measured_by_platform 加上理由），所以读的人总能分辨自己看的是哪一种。

Terminal-Bench 2 接入

这是最近完成的一次较大接入，也是把上面几条契约真正压到真实任务集上的一次。

89任务（本地上游 2fd12b8）
52 / 37train / eval 划分（按哈希）
3镜像在当前网络下拉不下来

接入过程中被真实任务集逼出来的设计决定：

布局容错

任务目录可能直接在根，也可能在 tasks/ 下 —— 两种都认。 上游仓库结构变过一次，硬编码一种就会在某天静默地少发现一半任务。

没有 compose 文件

代码里一个 custom_docker_compose 标志曾经指向一个 在任何地方都不存在的 compose 文件。整个 89 任务集里没有任何 compose —— 那个标志是空的。

验证容器必须能联网

89/89 个 test.sh 都会安装依赖。 验证容器原本用默认的 network="none" 创建，那会让所有 89 道题静默得零分。 现在按任务声明的网络来建。

docker cp 的目录语义

docker cp <dir>/. 里的点 被 pathlib 吃掉了，内容落到了 /app/setup 而不是 /app。加 contents=True。

顺序

mkdir_in 必须在 start 之后；/tests 在真实镜像里不存在，是平台负责拷进去。

能力门禁排在镜像解析之前

顺序曾经是反的，于是一只结构上不可能工作的 harness 会被指示去导入镜像；用户导完一个，回来被指示导入下一个。实测：两次 UI 运行、两个不同的缺失镜像， 而真正的原因（这只 harness 只声明了 files）从未出现。

构建中修掉的真缺陷

这一节是这台仪器的费用清单。它们大多不是「写错了」，而是两个都对的东西接在一起就不对：

症状真实原因
只选了一题，却被另一题的镜像拒掉 收窄只做了任务清单，三个 per-task 表仍是整个数据集的
run 目录里混着上一次运行的轮次 覆盖时只截断了 console.log，round*_base/、round*_ws/ 都留着 —— 新的一次轮数更少时，残留成了这次记录的一部分
eval 的轨迹被丢掉 _save_traces 只写 train 侧，25 条 eval 轨迹被丢弃
导入镜像 67 次全部瞬间失败 import_env.py 里少了 import os；而且异常被 except Exception 吞掉

共同的形状。这些缺陷里没有一个会产生异常，也没有一个会被「服务端测试全绿」 挡住 —— 它们都是静默地量错了东西。所以这个项目的测试重点不在覆盖率，而在 「这条规则有没有一件具体的事钉住它」。

尚未设计的东西

写下没做的事，和写下做了的事一样是这份文档的一部分。

  • 多容器环境（§2.5.10）—— 一个任务需要几个互相编排的容器时怎么办，还没有设计。
  • replay 路线 —— 已经不再维护。它留下的读数还在，能力不在了。
  • 「数据集声明一个镜像」与「harness 声明依赖」之间的调和 —— 镜像是为某只 harness 构建的（loop 需要 openai，裸 python 镜像里没有）， 这个耦合被记在数据集里而不是藏起来，但平台还没有机制去调和它。这是一个已知的开放设计点， 不是被这个 demo 解决的问题。
  • 3 个拉不下来的 Terminal-Bench 镜像 —— 外部网络限制。 界面把它们明确标成不可跑并写明原因，不会让你选中了才被拒。

依赖

bubblewrap git python3 ≥ 3.10 平台本身零第三方 Python 包

全部依赖就这三样。平台用的每一样东西都在标准库里。openai 只被参考 harness 的模型调用惰性导入，所以一只用别的语言、或对着别的提供方写的 harness 永远不需要它。

install.sh 不会停在「bwrap 装上了」，因为那不等于沙箱能工作： 一个禁用了非特权用户命名空间的内核，或一条限制它们的 AppArmor 策略（较新 Ubuntu 的默认）， 会让 bwrap 存在却在运行时失败。所以它最后会要求平台真的建一个命名空间、 并在里面找自己。失败就说清原因、拒绝称这台机器已就绪 —— 而不是让一次运行降级到 --no-sandbox 去产生含义与自称不符的数字。
